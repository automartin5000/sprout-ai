# Contributing to Sprout

How to set up a dev environment, run the build/test loop, and where things live in the codebase.

For the conceptual overview, read [ARCHITECTURE.md](./ARCHITECTURE.md) first — this file assumes you've read it.

---

## Dev setup

### Prerequisites

| Tool | Why | Install |
|---|---|---|
| macOS 14+ | Sprout is Mac-only | (you have it) |
| Node 22+ | Runs projen + Vite + electron-builder | `nvm install 22` or `brew install node@22` |
| Bun 1.0+ | The package manager + script runner | `curl -fsSL https://bun.sh/install \| bash` |
| Xcode Command Line Tools | Needed for native modules + codesigning | `xcode-select --install` |

You do **not** need to install AWS CLI, git, or Podman separately — those are bundled into the `.dmg` at packaging time and shimmed into `PATH` at runtime. Your dev shell uses your system versions of those tools.

For testing AI integrations:

- **Claude** — install Claude Code (`~/.claude` exists) OR set `ANTHROPIC_API_KEY` in your shell.
- **Copilot** — install the Copilot CLI: `brew install --cask copilot-cli` (or from `cli.github.com`).
- Without either, the AI dropdown only offers "Demo" mode (canned responses).

### First-time clone

```bash
git clone <repo-url> sprout
cd sprout
bun install              # installs deps + runs projen post-install
pj app:dev               # launches Electron with Vite hot-reload
```

`pj` is the projen task runner (we use `pj` as a shorthand alias — it maps to `npx projen <task>` or `bun .projenrc.ts <task>`). All custom tasks are defined in `.projenrc.ts`.

If `pj` isn't on your PATH, the canonical form works everywhere: `bun .projenrc.ts <task>` (e.g. `bun .projenrc.ts app:dev`).

### What `pj app:dev` does

1. Boots the local dynalite (mock DynamoDB) server.
2. Compiles the Electron main process via esbuild (watch mode).
3. Starts Vite for the renderer with HMR.
4. Launches Electron pointed at `http://localhost:5173`.

Edit any file under `app/renderer/` — hot-reloads. Edit `app/main/` — esbuild rebuilds; restart Electron manually (⌘Q in the app + re-run `pj app:dev`) since the main process can't hot-reload.

`MOCK_AUTH=1` is set automatically in dev mode, so you skip Auth0 and land on a fake "dev-user" session.

To run against the deployed sandbox stack with real Auth0:

```bash
SPROUT_USE_DEPLOYED=1 pj app:dev
```

See [runbooks/auth0-e2e.md](./runbooks/auth0-e2e.md) for the setup.

## The build / test loop

**`pj build` after every task** — this is the project's convention, not optional. It runs:

1. `typecheck` — `tsc --noEmit --strict --project tsconfig.dev.json` across all source.
2. `compile` — esbuild bundles for the Lambda, the runtime, the edge router, and the Electron renderer + main.
3. `eslint` — across `app/`, `lambda/`, `infra/`, `runtime/`, `shared/`, `scripts/`, `tests/`.
4. `vitest run` — the test suite.

If any step fails, the build fails. CI runs the same `pj build`, so green locally means green in CI.

### Targeted commands during development

| Command | When |
|---|---|
| `pj test` | Quick test loop. Vitest in run-once mode. |
| `pj test:watch` | Iterating on a single test file. Vitest watch mode. |
| `pj typecheck` | Just the TS check, ~3s. |
| `pj eslint` | Just lint, ~5s. |
| `pj lambda:build` | Just the Lambda bundle. Useful when iterating on `lambda/` against a deployed stack. |
| `pj runtime:build` | Just the runtime + edge-router bundles. |
| `pj app:build` | Just the Electron renderer + main bundle. |

`bun add <pkg>` adds dependencies; afterwards run `bun .projenrc.ts` once to regenerate `package.json` (projen owns it).

### Don't modify package.json directly

`package.json` is generated by projen. Edit `.projenrc.ts` and run `bun .projenrc.ts` to regenerate. Scripts, deps, dev-deps, and metadata are all controlled there.

The one exception: editing the projen-generated `package.json` in a fresh user project (when scaffolding via `sprout:new-app`) — the bundled template uses `project.package.setScript()` calls in its own `.projenrc.ts` so the dev scripts survive `bun projen` regeneration. See `plugins/sprout-cicd-github/templates/.projenrc.ts` for the pattern.

## Project layout

```
sprout/
├── .projenrc.ts          ← Project config. Tasks, deps, eslint, tsconfig
├── electron-builder.yml  ← .dmg packaging config
├── cdk.json              ← CDK entrypoint pointer
│
├── app/                  ← The Electron desktop app
│   ├── main/             ← Main process (Node). Owns everything except UI.
│   ├── preload/          ← contextBridge — the IPC boundary
│   ├── renderer/         ← React + Vite UI
│   └── resources/        ← Bundled binaries + plugins (populated by build)
│
├── lambda/api/           ← Hono backend, deployed via SproutStack
├── runtime/              ← Shared runtime Lambda + Lambda@Edge router
├── infra/lib/            ← CDK stacks (SproutStack, the multi-tenant infra)
│
├── plugins/              ← Source-of-truth plugin directories
│   ├── sprout/           ← The bundled starter plugin (provides sprout:new-app)
│   ├── sprout-cicd-github/        ← Default GitHub Actions deploy provider
│   └── sprout-cicd-jenkins-example/  ← Reference layout (not auto-loaded)
│
├── shared/               ← zod schemas + env config shared by main + lambda
├── scripts/              ← Build helpers (download-binaries, sanitize, etc.)
│
├── tests/                ← Vitest unit tests (~95 today)
├── test/                 ← Jest integration tests (run against dynalite)
└── e2e/                  ← Playwright E2E (drives the packaged .app)
```

### Where to find things

- "How does the AI agent see tools?" → `app/main/harness/`
- "What does the chat UI render for a tool call?" → `app/renderer/chat/ChatPane.tsx:inferActionCard()`
- "What does the AI's system prompt say?" → `app/main/services.ts:SPROUT_SYSTEM_PROMPT`
- "How does a project go from chat to live preview?" → `app/main/services.ts:projects:create` + `app/main/projects/dev-server.ts`
- "How does Share preview to sandbox actually publish?" → `app/main/publish/client.ts` + `lambda/api/routes/publish.ts`
- "How does Promote to prod scaffold a GitHub repo?" → `app/main/deploy/prod-client.ts`
- "How does the runtime Lambda route a request?" → `runtime/handler.ts` + `runtime/edge-router.ts`
- "What env vars does AI-generated code read?" → `plugins/sprout/skills/new-app/SKILL.md` (the load-bearing source of truth)

## Testing

### Vitest unit tests (`tests/`)

`tests/` mirrors the source tree. Add a test for any non-trivial behavior. The convention is one `.test.ts` per source unit:

- `tests/copilot-adapter.test.ts` — covers stream → event normalization, noise-tool filtering, error handling.
- `tests/worktree-restore.test.ts` — covers the non-destructive checkpoint restore.
- `tests/edge-router.test.ts` — covers path parsing, static-vs-api routing, SigV4 body hashing.

Pattern: fake external deps with `vi.mock()` at the top, test the unit's logic. Avoid network I/O; if something genuinely needs a real subprocess (rare), spawn a tiny one inside the test.

### Jest integration (`test/`)

Used for backend tests that need a real DynamoDB. Spins up dynalite or AWS SDK against an in-process server. Slower; run with `pj test:integration`.

### Playwright E2E (`e2e/`)

Drives the packaged `.app`. Used sparingly — slow, flaky, hard to debug. Useful for the "did the dmg actually launch and respond to a click" smoke. Run with `pj e2e`.

### What's *not* tested

- Visual regression — no Playwright screenshot tests yet. UI changes are manually smoke-tested.
- Codesigning + notarization — only verified by hand on release builds.
- Real AWS deployment — verified manually via `DEPLOY_ENV=dev pj deploy` against a personal account. CI doesn't deploy.

See `TEST-COVERAGE-AUDIT.md` at the repo root for the honest current-state breakdown.

## Common contributions

### Add a new IPC channel

1. Define the channel in `app/main/ipc.ts`'s `ApiSurface` interface (typed input + return).
2. Implement the handler on `Services` (`app/main/services.ts`).
3. Expose it through the preload bridge (`app/preload/index.ts`).
4. Add the typed accessor to `app/renderer/global.d.ts`.
5. Use `window.sprout.<channel>()` from the renderer.
6. Add a test in `tests/services-*.test.ts` covering the new method's logic.

The bridge is fully typed end-to-end — if you forget a step, TypeScript complains.

### Add a new env var the AI's code can read

This is load-bearing and easy to mess up — see [AGENTS.md § Add a new env var the AI's code can read](../AGENTS.md#add-a-new-env-var-the-ais-code-can-read) for the four places that must agree.

### Add a new test fixture

Fixtures live in `tests/fixtures/`. The pattern is one directory per fixture, containing whatever shape the test needs (a fake plugin, a fake project, etc.). Reference them via `path.join(__dirname, 'fixtures', 'foo')`.

### Update the AI's system prompt

It's a string in `app/main/services.ts`. Two cautions on the bad/good description list — see [AGENTS.md § Change the system prompt](../AGENTS.md#change-the-system-prompt).

### Touch the runtime Lambda

`runtime/handler.ts` is the shared Lambda. Every test in `tests/runtime-handler.test.ts` should stay green; if you add new behavior, add a test. After deploying (`DEPLOY_ENV=dev pj deploy`), smoke-test by hitting the CloudFront URL for a real project.

The runtime is **load-bearing for tenancy**: it sets `process.env.SPROUT_PROJECT_ID` per request from the `X-Sprout-Project-Id` header (which CloudFront-Origin-OAC-trust ensures is set only by the edge router). Don't read project IDs from anywhere else inside the runtime.

## Commit message conventions

No strict format. Aim for:

- Imperative present tense ("Fix preview retry timing", not "Fixed" or "Fixes")
- A one-line subject under 70 chars
- A body explaining *why*, not *what* (the diff shows what)

Example:

```
Tune preview retry timing to avoid showing in-progress template state

The first retry at 500ms caught the template's default scaffold before
the AI's edits landed, so users saw the template state momentarily
before the final app appeared. New backoff is [2500, 3500, 5000, 8000,
12000] which gives Vite's restart-on-edit cycle enough time to settle
before each attempt.
```

No DCO sign-off required.

## Things that look like bugs but aren't

- **The renderer can't access `fs` or `child_process`.** That's the contextIsolation boundary. Add an IPC channel.
- **Edits to `app/main/*` don't hot-reload.** Electron's main process can't be hot-reloaded. Quit (⌘Q) and re-run `pj app:dev`.
- **`pj build` rebuilds everything even when nothing changed.** Projen's task system isn't incremental for our custom tasks. Use `pj test` or `pj typecheck` for targeted loops.
- **The Mock harness is always present in the dropdown.** Intentional — gives demo paths a stable fallback even when no AI credentials are configured.
- **`bun add <pkg>` doesn't update package.json**. It does — but projen will overwrite it on next regenerate. Add the dep to `.projenrc.ts`'s `deps` or `devDeps` array, then run `bun .projenrc.ts`.
